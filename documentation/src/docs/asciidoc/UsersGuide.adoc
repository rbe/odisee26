== Users Guide

=== Clients

There's a http://www.odisee.de/odisee/product/odisee-client.xhtml[Windows client]
to test sending requests to Odisee. On the same page there are links to
Odisee client libraries (http://git.odisee.de/client-java/src[Java],
http://git.odisee.de/client-vbnet/src[VB.NET],
http://git.odisee.de/client-php/src[PHP]) along with examples how to use
the API.
The JavaFX screens are `clients/client-javafx` (login pane, main frame, and FXML).
They use the Java client in this repository (`org.odisee.client`).
`./gradlew :clients:client-javafx:run` starts the window.
JavaFX is on the module path for that launch.

==== Java

.Working with a single request
    :::java
    // Create Odisee client with service URL and Bearer token
    OdiseeClient odisee = OdiseeClient.bearer("http://127.0.0.1:8080/odisee/document/generate", token);
    // Create a new request for template HalloOdisee
    // By default, the last call to createRequest is remembered by the client
    odisee.createRequest("HalloOdisee", OutputFormat.PDF);
    // Set value for userfield "hallo"
    odisee.setUserfield("hallo", "Odisee");
    // Set value in table "Tabelle1" cell "A4"
    odisee.setTableCellValue("Tabelle1", "A4", "value in a table cell");
    // Generate document, PDF by default
    byte[] document = odisee.process(false);

.Working with multiple requests
    :::java
    // Create Odisee client with service URL and Bearer token
    OdiseeClient odisee = OdiseeClient.bearer("http://127.0.0.1:8080/odisee/document/generate", token);
    // First request
    Request firstRequest = odisee.createRequest("HalloOdisee", OutputFormat.PDF);
    odisee.setUserfield(firstRequest, "hallo", "Odisee");
    odisee.setTableCellValue(firstRequest, "Tabelle1", "A4", "value in a table cell");
    // Second request
    Request secondRequest = odisee.createRequest("HalloOdisee", OutputFormat.PDF);
    odisee.setUserfield(secondRequest, "hallo", "Odisee, again");
    odisee.setTableCellValue(secondRequest, "Tabelle1", "A4", "Another value in a table cell");
    // Generate document
    byte[] document = odisee.process(false);

.Using the fluent API
    :::java
    // Create Odisee client with service URL and Bearer token
    OdiseeClient odisee = OdiseeClient.bearer("http://127.0.0.1:8080/odisee/document/generate", token);

                             setUserfield("Salutation", "Mr.").

                             setUserfield("Zipcode", "12345").
                             setUserfield("City", "Berlin").
                             setUserfield("Subject", "This is a letter").
                             process(false);

=== Request contract

`POST /document/generate` is synchronous.
`odisee/@delivery` is `stream`, `store`, or `both`.
The default is `stream`.
For `stream` and `both`, the HTTP response is the generated document.
For `store`, the body is JSON `bucket` and `key`, and the file is only in the user's bucket.
`both` stores a copy, identified by the `X-Odisee-Object` header (`bucket/key`).
A request cannot name the bucket.
A synchronous generate deletes `var/user/{name}/output/{uuid}/` unless `archive/@files` is `true`.
A job keeps that directory.
`$ODISEE_HOME/etc/buckets` and the `minio` compose service are in the administrators guide, <<object-storage>>.
It validates XML against the v2 request schema (`http://xmlns.odisee.de/v2/request`).
A document with no namespace is that same shape.
The v3 namespace and the v2.6 namespace are HTTP 400.
`output/format` is part of v2.
`format/@type` is the file extension when it is present.
`template/@outputFormat` applies when `output` is absent.
`format/options/option` carries name/value pairs such as `pdf-version`, `tagged`, and `watermark`.
The `.pdfa` suffix remains the PDF/A fallback when the request did not set a PDF version.
The body of a failed request is plain text: the schema message.

A `DOCTYPE` is rejected.
External entities are not read.
The raw body, including gzip, is limited to 8 MiB.
The body after gzip is limited to 32 MiB.
Either limit is HTTP 400.

`HttpStatuses` chooses the status.
400 is a request the schema refused.
422 is an instruction the schema allowed and the office process could not run.
404 is a missing template.
503 is an office pool that could not take the call.
500 is an unexpected server error.

=== Jobs

`POST /document/jobs` returns HTTP 202 and a job id.
`GET /document/jobs/{id}` returns `status`, `failedInstruction`, and `file`.
Jobs are private to the caller.
The list is `var/user/{name}/jobs.json`.
A callback is a query parameter on `POST /document/jobs`.
`POST /document/generate` does not read a callback.
Odisee POSTs the status only when that host is listed for that user in `$ODISEE_HOME/etc/callback-hosts`.
`odictl callback-host USER HOST` appends a line.
A host listed for one user does not allow another user's callback.
A URL whose host is off that user's list does not get a POST.
The host must be a public external host. Loopback, link-local, private, and internal names are rejected.

=== Instructions

Writer, Calc, and Impress have separate instruction sets.
Writer keeps `Userfield`, `Texttable`, `Image`, `Autotext`, `Bookmark`, and `Macro`.
`image/@url` is `http` or `https` on a public host. `file://` and an internal host are HTTP 422.
Calc uses `cell`.
`cell` requires `sheet` and `coordinate`.
Impress uses `shape`.
`shape` requires `name`.
A tag from another application's set is HTTP 422.
There is no shared `named` tag.

=== JSON requests

XML is still the default, and it is still what the generator executes.
JSON is converted to that v2 document and validated with the same schema.
The same `POST /document/generate` endpoint also accepts JSON.
Send `Content-Type: application/json`.
A body that starts with `{` is treated as JSON when the content type is omitted.
Gzip works for both formats: the service looks at the gzip magic bytes before it reads the document.

JSON field names are camelCase.
They map onto the existing XML attributes (`preSaveMacro` becomes `pre-save-macro`, `postMacro` becomes `post-macro`, and so on).
`delivery` is the field for `odisee/@delivery`.
It sits on the same object as `request`.
The values are `stream`, `store`, and `both`.
The default is `stream`.
`instructions` is an array, and the array order is the order the instructions run.
`table` is accepted as an alias of `texttable`.
On an `input` step, `file` from older XML is sent as `filename`.

.One template, two user fields
[source,json]
----
{
  "request": {
    "name": "HalloOdisee",
    "template": { "name": "HalloOdisee", "outputFormat": "pdf" },
    "instructions": [
      { "instruction": "userfield", "name": "Hallo", "value": "Odisee" },
      { "instruction": "userfield", "name": "Tabelle1!A4", "value": "support@odisee.de" }
    ]
  }
}
----

[source,bash]
----
curl -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  --data-binary @HalloOdisee.json \
  -o HalloOdisee.pdf \
  http://127.0.0.1:8080/odisee/document/generate
----

A failed JSON request uses the same error response as XML: the status comes from the exception, and the body is the plain-text message.

The shape is described by `webservice/src/main/resources/json/request.schema.json`.
A request object needs `template.name`.
Each instruction needs `instruction` set to one of `userfield`, `texttable`, `image`, `autotext`, `bookmark`, `macro`, `cell`, or `shape`.
`cell` is Calc.
`shape` is Impress.
`output.format.type` is the extension when it is present.
`output.format.options` is a list of `{ "name", "value" }` pairs.
Macro arguments are a `parameter` array of strings or `{"value":"..."}` objects.
Post-processing looks like this:

[source,json]
----
"postProcess": {
  "action": [{
    "type": "merge-with",
    "content": [
      { "element": "result-placeholder" },
      { "element": "input", "filename": "pdf/AGB.pdf" }
    ]
  }]
}
----

`response.base64` is accepted and stored on the request.
For `stream` and `both`, the HTTP response is still the generated document itself.
For `store`, the body is the bucket and the key.

==== Clients

Call `useJson()` before `process()`.
The client libraries keep building the request the way they always have, then convert that XML to JSON for the POST.
Leave the call out and they keep sending XML.

.Java
[source,java]
----
OdiseeClient odisee = OdiseeClient.bearer("http://127.0.0.1:8080/odisee/document/generate", token);
odisee.useJson();
odisee.createRequest("HalloOdisee", OutputFormat.PDF);
odisee.setUserfield("Hallo", "Odisee");
byte[] document = odisee.process(false);
----

.PHP
[source,php]
----
$odisee = Odisee::bearer('http://127.0.0.1:8080/odisee/document/generate', $token);
$odisee->useJson();
$request = $odisee->createRequest('HalloOdisee');
$odisee->setUserfield($request, 'Hallo', 'Odisee');
$document = $odisee->process();
----

.Visual Basic .NET
[source,vbnet]
----
Dim odiseeClient As OdiseeClient = OdiseeClient.bearer(serviceUrl, token)
odiseeClient.useJson()
odiseeClient.createRequest("HalloOdisee")
odiseeClient.setUserfield("Hallo", "Welt")
Dim webResponse As HttpWebResponse = odiseeClient.process()
----

.Oracle
Call `odisee.set_bearer_token(token)` and `odisee.use_json` before `odisee.header`.
`odisee.generate` posts `Authorization: Bearer` to `/odisee/document/generate` with `application/json; charset=UTF-8`.
`odisee.use_xml` switches back to the v2 XML request shape (`http://xmlns.odisee.de/v2/request`).

=== Suggestions

A few follow-ups are worth doing while this interface is still young:

. Validate JSON against `request.schema.json` at the edge and return the failing field in `{"error":"..."}`. The converter already rejects unknown instructions and a missing template name; a schema check would cover the rest without another hand-written branch.
. Publish an OpenAPI description of `POST /document/generate` with both `application/json` and `text/xml` request bodies. The client libraries would then be able to grow from one description instead of each one owning a copy of the XML-to-JSON mapping.
. Honor `response.base64`. The field is accepted today and, for `stream` and `both`, the document is still returned as raw bytes. Callers that want a JSON conversation end to end need a base64 document (and, later, page count and template revision) selected with `Accept`.
. Keep XML as the execution format until a single in-memory request model replaces both the DOM walk and the JSON converter. Two encodings of one model drift; one model with two parsers does not.
