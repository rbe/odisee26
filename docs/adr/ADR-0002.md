# Per-request state, template lookup, and instruction sets

## Rule

- Each call gets a new map from `RequestContext.create()`. `RequestContext.resetForNextRequest` clears the template fields and keeps the documents of the same XML body. A singleton holds no request state.
- `SafePaths.resolveInside(root, relative)` keeps a template name and a merge input inside its root. An absolute path or `..` is rejected.
- `TemplateLocator` is the template lookup. Revisions are `var/user/{name}/template/{templateName}/rev/{n}.ott`. `LATEST` is the highest number across that directory and the flat `Name.ott` and `Name_revN.ott` files. `Name.ott` is revision 1. A missing revision is HTTP 404.
- When a Writer file and a Calc or Impress file have the same name, `Name.ott` wins.
- Each application has its own instruction set. Writer has `Userfield`, `Texttable`, `Image`, `Autotext`, `Bookmark`, and `Macro`. Calc has `cell`. Impress has `shape`. There is no shared tag. A tag from another set is HTTP 422.
- Post-process actions are `merge-with` and `merge-results` only. No tag or action name becomes a method name.
- A failed instruction fails the request with HTTP 422. The office document is closed first, and no file is saved.
- `POST /document/generate?dryRun=true` applies the instructions and saves no file under `output`.

## Why

Wave 1 found a shared document list across requests, lexicographic revision order, path escapes, and dispatch by string (old labels B1, B2, B4, B5, B23, B24). Small pure types (`RequestContext`, `SafePaths`, `TemplateLocator`, `OutputFormats`) carry these decisions, so unit tests check them without LibreOffice.
